## 1. 架构概述

### 1.1 系统定位

**系统名称**：团队任务管理系统（Task Management System）

**系统定位**：
为12人软件开发团队提供统一的任务管理平台，解决任务分配不明确、进度不透明、沟通信息分散的痛点，支持任务全生命周期管理、多视图展示、协作沟通和Sprint迭代管理。

**核心价值**：
- **提升协作效率**：任务分配明确，责任清晰，减少推诿和沟通成本
- **增强进度透明**：实时掌握团队工作状态，支持管理层快速决策
- **保障数据安全**：私有化部署，数据完全在企业内网，符合企业安全要求
- **降低管理成本**：替代分散的Excel/Trello/微信等工具，统一数据管理

### 1.2 核心设计理念

**设计原则**：

1. **分层清晰，职责单一**（Separation of Concerns）
   - 采用经典三层架构（表示层、业务逻辑层、数据访问层），每层职责明确
   - 表示层专注UI交互，业务层处理核心逻辑，数据层负责持久化
   - 层间依赖单向（上层依赖下层），降低耦合度

2. **安全第一，权限严控**（Security by Design）
   - 所有API端点强制认证（JWT Token）
   - 基于角色的权限控制（RBAC），管理员和成员权限分离
   - 敏感数据加密存储（BCrypt密码、HTTPS传输）
   - 全面审计日志，关键操作可追溯

3. **快速交付，迭代优化**（MVP First）
   - 11周交付MVP，优先实现核心功能（任务CRUD、权限管理、基础视图）
   - 架构设计支持未来扩展（微服务化、实时通知），但不过度设计
   - 采用成熟技术栈（Spring Boot + Vue），降低学习成本和交付风险

4. **数据驱动，指标可量化**（Data-Driven）
   - 所有性能指标明确量化（页面加载<3秒、API响应<500ms）
   - Sprint进度可视化，支持燃尽图、统计报表
   - 审计日志记录完整，支持用户行为分析

5. **容错优雅，体验友好**（Graceful Degradation）
   - 前端输入校验 + 后端参数校验双重保障
   - 异常情况返回友好错误提示，不暴露技术细节
   - 数据库连接失败、网络超时等场景有降级方案

### 1.3 架构风格

**主要架构风格**：分层架构（Layered Architecture）

**选择理由**（追溯ADR-001）：

1. **技术栈匹配**：Spring Boot天然支持分层架构，Controller/Service/Repository职责分明，符合团队开发习惯
2. **团队熟悉度高**：12人团队中3人有Java分层架构经验，学习曲线平缓
3. **可扩展性好**：分层架构便于未来演进（如引入缓存层、消息队列层），横向扩展成本低
4. **开发效率高**：每层可并行开发，前端（表示层）和后端（业务层+数据层）团队协作明确

**架构层次定义**：

```
┌──────────────────────────────────────┐
│   表示层（Presentation Layer）        │
│   - Vue 3 前端应用                   │
│   - Element Plus UI组件              │
│   - Axios HTTP客户端                 │
└──────────────────────────────────────┘
              ↓ HTTP/REST API
┌──────────────────────────────────────┐
│   应用层（Application Layer）         │
│   - Spring Boot Controller           │
│   - 请求参数校验                     │
│   - JWT认证拦截                      │
└──────────────────────────────────────┘
              ↓
┌──────────────────────────────────────┐
│   业务逻辑层（Business Logic Layer） │
│   - Spring Service组件               │
│   - 业务规则校验                     │
│   - 事务管理（@Transactional）       │
└──────────────────────────────────────┘
              ↓
┌──────────────────────────────────────┐
│   数据访问层（Data Access Layer）     │
│   - MyBatis-Plus Mapper              │
│   - 数据库CRUD操作                   │
│   - SQL优化与缓存                    │
└──────────────────────────────────────┘
              ↓
┌──────────────────────────────────────┐
│   数据层（Data Layer）               │
│   - MySQL 8.0数据库                  │
│   - InnoDB存储引擎                   │
└──────────────────────────────────────┘
```

### 1.4 系统边界

**系统范围**：

- ✅ **包含功能模块**：
  - **用户与权限管理**：用户登录、账号管理、角色分配、密码修改、审计日志（来自用户故事US001-US004, US025）
  - **任务管理核心**：任务CRUD、分配负责人、状态更新、操作历史记录（来自用户故事US005-US011）
  - **多视图展示**：任务列表视图、看板视图、拖拽状态更新（来自用户故事US012-US014）
  - **搜索与筛选**：关键词搜索、多维度筛选（状态/优先级/负责人/标签）、筛选偏好保存（来自用户故事US015-US016）
  - **协作与通知**：任务内评论、@提及、系统通知、通知中心（来自用户故事US018, US020）
  - **Sprint管理**：Sprint创建、任务分配到Sprint、进度统计（来自用户故事US022-US024）

- ❌ **不包含功能**（未来版本）：
  - ❌ 任务依赖关系管理（如"任务A必须在任务B之前完成"）
  - ❌ 甘特图视图（时间轴展示）
  - ❌ 工时统计与报表（如"本周开发团队总工时"）
  - ❌ 邮件通知（仅站内通知，不发送邮件）
  - ❌ 第三方系统集成（如GitLab、Jenkins）
  - ❌ 移动端原生App（仅Web响应式设计）
  - ❌ 多租户支持（仅支持单个企业团队）

**系统边界说明**（追溯ADR-001 §背景）：
- MVP阶段聚焦核心任务管理和协作功能，确保11周内交付可用系统
- 不包含的功能已列入产品路线图（V2.0规划），避免过度设计导致交付延期
- 系统仅面向单个12人团队，不考虑多租户场景，简化权限设计和数据隔离

**依赖说明**：

- **Sprint服务 ↔ 搜索服务**：Sprint进度统计依赖任务搜索能力

#### 关键设计决策

1. **前后端分离设计**（追溯ADR-001）
   - **决策内容**：前端Vue SPA单独部署，后端Spring Boot提供RESTful API，通过JSON交互
   - **理由**：前后端团队并行开发，Vue和Spring Boot技术栈解耦，便于独立升级和扩展
   - **架构体现**：表示层（Vue）和应用层（Controller）通过HTTP协议通信，无服务端模板渲染

2. **Service层事务管理**（追溯Spring Boot最佳实践）
   - **决策内容**：所有涉及数据库写操作的Service方法添加`@Transactional`注解
   - **理由**：确保数据一致性（如"创建任务+记录历史"必须原子性执行），失败自动回滚
   - **架构体现**：业务逻辑层统一管理事务边界，数据访问层只负责单表操作

3. **MyBatis-Plus代码生成**（追溯ADR-001 §缓解措施）
   - **决策内容**：使用MyBatis-Plus代码生成器自动生成Mapper/Service/Controller基础代码
   - **理由**：减少样板代码编写，提升11周MVP交付效率
   - **架构体现**：数据访问层的CRUD方法由MyBatis-Plus自动生成，开发者仅需编写复杂查询SQL

4. **全局异常处理**（追溯设计原则§容错优雅）
   - **决策内容**：使用`@ControllerAdvice`统一捕获业务异常、数据库异常、参数校验异常
   - **理由**：避免Controller层重复try-catch，返回统一的错误响应格式
   - **架构体现**：公共基础模块的`GlobalExceptionHandler`拦截所有异常，转换为友好的JSON响应

5. **审计日志异步记录**（追溯设计原则§性能优先）
   - **决策内容**：审计日志记录使用Spring `@Async`异步执行，不阻塞主业务流程
   - **理由**：日志写入失败不应影响用户操作（如任务创建成功，日志写入失败不应回滚任务）
   - **架构体现**：AuditLogService使用线程池异步记录，与主业务事务隔离

### 2.3 数据视图（Data View）

**目标**：展示系统的数据流转和存储设计。

#### 数据流转图

```
┌─────────────┐
│   用户      │ 1. 登录请求
└─────────────┘
       ↓
┌─────────────────────────────────────┐
│  AuthController                     │ 2. 校验账号密码
│  - 验证账号密码（BCrypt对比）       │
│  - 生成JWT Token（30分钟有效期）    │
└─────────────────────────────────────┘
       ↓
┌─────────────────────────────────────┐
│  UserService                        │ 3. 查询用户信息
│  - 从数据库查询用户                 │
│  - 加载用户角色和权限                │
└─────────────────────────────────────┘
       ↓
┌─────────────────────────────────────┐
│  MySQL数据库                        │ 4. 返回用户数据
│  - users表：用户基本信息            │
│  - user_roles表：用户角色关联       │
└─────────────────────────────────────┘
       ↓
┌─────────────────────────────────────┐
│  前端Vue应用                        │ 5. 存储Token
│  - LocalStorage存储JWT Token        │
│  - 后续请求Header携带Token          │
└─────────────────────────────────────┘
```

**数据流转说明**：
1. **用户操作 → 前端校验 → 后端处理 → 数据库存储**：所有写操作经过前后端双重校验
2. **读操作缓存**（预留扩展）：高频读取数据（如任务列表）可引入Redis缓存，减轻数据库压力
3. **事件驱动**（预留扩展）：@提及触发通知采用发布-订阅模式，Service层发布事件，NotificationService异步消费

#### 数据存储设计

### 2.5 场景视图（Scenario View）

**目标**：展示关键业务场景的架构流程。

#### 场景1：用户创建任务

**业务流程**（追溯US005）：

1. 用户在任务列表页点击"新建任务"按钮
2. 弹出任务创建表单，填写任务标题、描述、优先级、截止日期、负责人
3. 前端校验表单必填项（标题、描述不为空）
4. 提交表单，发送POST请求到后端API `/api/v1/tasks`
5. 后端Controller接收请求，参数校验（`@Valid`）
6. TaskService执行业务逻辑：
   - 6.1 创建任务记录，保存到`tasks`表
   - 6.2 创建任务历史记录，保存到`task_history`表（操作类型：CREATE）
   - 6.3 如果指定了负责人，触发通知（异步）
7. 事务提交，返回任务ID
8. 前端接收成功响应，刷新任务列表，显示新建任务

**架构组件交互**：

```
[前端Vue] → POST /api/v1/tasks → [TaskController]
                                        ↓
                                   [TaskService] (事务开始)
                                        ↓
                               [TaskMapper.insert(task)]
                                        ↓
                                   [MySQL tasks表]
                                        ↓
                         [TaskHistoryService.recordCreate(task)]
                                        ↓
                                [MySQL task_history表]
                                        ↓ (如果有负责人)
                           [NotificationService.notifyAssignment]
                                    (异步执行)
                                        ↓
                                [MySQL notifications表]
                                        ↓
                                 (事务提交)
                                        ↓
                               [返回任务ID给前端]
```

**性能要求**（追溯ADR-001 §性能约束）：
- API响应时间：P95 < 500ms（包含数据库写入时间）
- 数据库插入时间：< 100ms（单条INSERT）
- 通知发送：异步执行，不阻塞主流程

#### 场景2：用户查看任务列表（分页+筛选）

**业务流程**（追溯US012, US016）：

1. 用户访问任务列表页
2. 前端发送GET请求：`/api/v1/tasks?page=1&size=20&status=IN_PROGRESS&priority=HIGH&assigneeId=5`
3. 后端Controller接收分页参数和筛选条件
4. TaskService构建查询条件（MyBatis-Plus QueryWrapper）
5. TaskMapper执行SQL查询（带WHERE条件和LIMIT分页）
6. MySQL返回任务列表（20条）和总记录数
7. 后端封装分页响应（`{ data: [...], total: 150, page: 1, size: 20 }`）
8. 前端接收数据，渲染任务列表和分页器

**架构组件交互**：

```
[前端Vue] → GET /api/v1/tasks?filters → [TaskController]
                                              ↓
                                        [TaskService]
                                              ↓
                            [TaskMapper.selectPage(queryWrapper)]
                                              ↓
                                    [MySQL查询（带索引）]
                  SELECT * FROM tasks WHERE status='IN_PROGRESS'

                                              ↓
                                      [前端渲染列表]
```

**性能要求**：

- 数据库查询时间：< 100ms（通过索引优化：`idx_status_priority_assignee`）

#### 场景3：用户在看板拖拽任务更新状态

**业务流程**（追溯US014）：

1. 用户在看板视图拖拽任务卡片，从"待办"列移动到"进行中"列
2. 前端Vue拖拽事件监听器触发
3. 前端发送PUT请求：`/api/v1/tasks/123/status`，Body: `{ status: 'IN_PROGRESS' }`
4. 后端Controller接收请求，参数校验
5. TaskService执行状态更新：
   - 5.1 查询任务当前状态（旧状态：TODO）
   - 5.2 更新任务状态为IN_PROGRESS
   - 5.3 记录任务历史（操作类型：STATUS_CHANGE，旧值：TODO，新值：IN_PROGRESS）
   - 5.4 触发通知（异步）：通知任务负责人状态变更
6. 事务提交，返回成功响应
7. 前端乐观更新UI（立即移动卡片位置），收到成功响应后确认

**架构组件交互**：

```
[前端Vue拖拽] → PUT /api/v1/tasks/123/status → [TaskController]
                                                       ↓
                                                 [TaskService]
                                                       ↓
                                       [TaskMapper.updateStatus(123)]
                                                       ↓
                                               [MySQL UPDATE]
                              UPDATE tasks SET status='IN_PROGRESS'
                                   WHERE id=123
                                                       ↓
                                    [TaskHistoryService.recordStatusChange]
                                                       ↓
                                          [MySQL INSERT task_history]
                                                       ↓
                                         [NotificationService (异步)]
                                                       ↓
                                              [返回成功响应]
```

**性能要求**：
- 拖拽响应时间：< 200ms（前端乐观更新，用户感知延迟<50ms）
- 数据库更新时间：< 50ms（通过主键索引快速定位）
- 前端动画流畅度：60fps

### 5.2 架构设计理由

#### 分层架构选择

**理由**：
1. **技术栈匹配**：Spring Boot天然支持MVC分层，Controller/Service/Repository职责清晰
2. **团队熟悉**：12人团队中3人有Java分层架构经验，学习曲线平缓
3. **可扩展**：分层架构便于未来引入缓存层、消息队列层，横向扩展成本低
4. **开发效率**：每层可并行开发，前后端团队协作明确

**追溯**：
- ADR-001 §决策：选择Java + Spring Boot生态
- 设计原则 §1：分层清晰，职责单一

#### 审计日志异步记录

**理由**：
1. **性能优先**：日志写入不阻塞主业务流程（如任务创建）
2. **用户体验**：日志失败不影响用户操作成功
3. **弹性设计**：日志服务独立线程池，与主业务事务隔离

**追溯**：
- 设计原则 §5：容错优雅，体验友好
- §2.1关键决策5：审计日志异步记录

#### 前后端分离部署

**理由**：
1. **技术解耦**：Vue和Spring Boot独立升级，互不影响
2. **并行开发**：前后端团队同时开发，提升效率
3. **静态资源优化**：前端静态文件Nginx直接托管，减轻后端压力

**追溯**：
- ADR-001 §决策：Vue 3 + Spring Boot前后端分离
- §2.1关键决策1：前后端分离设计

## 6. 架构风险与应对

### 6.1 风险清单

| 风险ID | 风险描述 | 概率 | 影响 | 等级 | 应对措施 | 追溯 |
|--------|---------|------|------|------|---------|------|
| **R1** | Spring Boot学习成本导致开发延期 | 中 | 高 | 🟡 | 第1周集中培训（1周），使用代码生成器减少样板代码 | ADR-001 §风险 |
| **R2** | JVM内存占用超标（>1GB） | 中 | 中 | 🟡 | 优化JVM参数（-Xms512m -Xmx1GB），服务器升级8GB内存 | ADR-001 §缓解措施 |
| **R3** | MySQL性能瓶颈（慢查询） | 低 | 高 | 🟡 | 添加索引（status/assignee_id），引入Redis缓存（V2.0） | §3.1性能要求 |
| **R4** | 并发用户数超100导致系统卡顿 | 低 | 中 | 🟢 | Tomcat线程池调优（最大线程150），MySQL连接池扩容 | §4.2资源约束 |
| **R5** | 前端首屏加载慢（>3秒） | 中 | 中 | 🟡 | 路由懒加载，Gzip压缩，图片懒加载 | §3.1性能要求 |
| **R6** | 安全漏洞（SQL注入/XSS） | 低 | 高 | 🟡 | 代码审查（强制参数化查询），安全测试（渗透测试） | §3.4安全性 |
| **R7** | 数据备份恢复失败 | 低 | 高 | 🟡 | 定期演练备份恢复流程（每月1次），保留30天备份历史 | §4.1技术约束 |

### 6.2 回滚方案

**核心回滚策略**（追溯ADR-001 §回滚条件）：

1. **开发进度延误（第6周完成人日<35人日）**：
   - **回滚方案**：切换到Node.js + Express方案（2周切换时间）
   - **执行步骤**：
     - 第1周：Node.js环境搭建，Express项目脚手架初始化
     - 第2周：迁移已完成的Java业务逻辑到Node.js
   - **预计影响**：延期2周，总工期13周

2. **性能不达标（API响应P95>800ms）**：
   - **回滚方案**：优化Java方案（1周优化时间）
   - **执行步骤**：
     - 数据库索引优化（添加复合索引）
     - 引入Redis缓存高频查询数据
     - JVM调优（G1GC垃圾回收器）
   - **预计影响**：无延期，在第8-9周执行优化

3. **内存占用超标（JVM>2GB）**：
   - **回滚方案**：服务器内存升级（1天完成）
   - **执行步骤**：
     - 购买内存条（8GB→16GB）
     - 重启服务器，调整JVM参数（-Xmx2GB）
   - **预计影响**：额外成本2000元，无延期

## 7. 架构演进路线

### 7.1 当前架构（MVP/V1.0）

**核心特征**：
- ✅ 分层架构，前后端分离，单体应用
- ✅ 私有化内网部署，MySQL单库存储
- ✅ HTTP轮询实现通知（每30秒轮询一次）
- ✅ 11周快速交付，满足核心任务管理需求

**限制**：
- ❌ 不支持实时通知（WebSocket）
- ❌ 不支持任务依赖关系管理
- ❌ 不支持甘特图视图
- ❌ 不支持工时统计与报表

---

### 7.2 未来架构（V2.0）

**演进目标**：
- 🔄 引入WebSocket实现实时通知（替代HTTP轮询）
- 🔄 引入Redis缓存，优化高频查询性能
- 🔄 增加任务依赖关系管理（DAG有向无环图）
- 🔄 增加甘特图视图（时间轴展示）

**架构变化**：

```
当前架构（V1.0）
┌──────────┐
│ Vue前端   │ ← HTTP轮询通知
└──────────┘
      ↓
┌──────────┐
│ SpringBoot│
└──────────┘
      ↓
┌──────────┐
│  MySQL   │
└──────────┘

↓ 演进

未来架构（V2.0）
┌──────────┐
│ Vue前端   │ ← WebSocket实时通知
└──────────┘
      ↓
┌──────────┐     ┌─────────┐
│ SpringBoot│ ←→ │ Redis   │ (缓存层)
└──────────┘     └─────────┘
      ↓
┌──────────┐
│  MySQL   │
└──────────┘
```

**演进时间表**：
- **2026年Q3（V1.1）**：引入Redis缓存，优化任务列表查询性能
- **2026年Q4（V2.0）**：WebSocket实时通知，任务依赖关系管理
- **2027年Q1（V2.1）**：甘特图视图，工时统计与报表

| 技术债务 | 说明 | 优先级 | 计划偿还时间 |
