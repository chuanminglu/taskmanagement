## 📐 C4模型说明

C4模型是一种分层架构可视化方法，包含4个层次：

| 层次              | 英文名称  | 中文名称     | 目标受众           | 抽象级别 | 典型元素数量 |
| ----------------- | --------- | ------------ | ------------------ | -------- | ------------ |
| **Level 1** | Context   | 系统上下文图 | 管理层、非技术人员 | 最高     | 3-8个        |
| **Level 2** | Container | 容器图       | 架构师、技术经理   | 高       | 5-10个       |
| **Level 3** | Component | 组件图       | 开发团队           | 中       | 8-15个       |
| **Level 4** | Code      | 代码图       | 开发者             | 低       | 通常不绘制   |

## 🎨 图例说明

- **蓝色框**：系统内部的组件/容器
- **灰色框**：外部系统/服务
- **人形图标**：用户角色
- **实线箭头**：同步调用
- **虚线箭头**：异步调用
- **标注文字**：描述交互内容（如"提交需求"、"调用API"）

### 技术交互流程

1. **用户访问流程**：

   - 用户通过浏览器访问 `https://task.company.local`
   - Nginx接收HTTPS请求（TLS 1.2+加密）
   - 静态资源请求（HTML/CSS/JS）→ Nginx直接返回
   - API请求（`/api/*`）→ Nginx转发到Spring Boot API服务
2. **API调用流程**：

   - 前端Vue应用发送HTTP请求（携带JWT Token）
   - API服务验证Token，执行业务逻辑
   - 通过MyBatis-Plus访问MySQL数据库
   - 返回JSON格式响应给前端
3. **数据备份流程**：

   - Linux cron定时任务每日凌晨2点触发
   - mysqldump全量导出MySQL数据
   - 备份文件存储到备份服务器，保留30天

### 关键设计模式

#### 1. 分层架构模式

```
Controller（API端点）→ Service（业务逻辑）→ Mapper（数据访问）→ Database
```

**优势**（追溯SAD §1.3）：

- ✅ 职责清晰，每层关注单一责任
- ✅ 层间解耦，便于单元测试
- ✅ 可独立演进，如引入缓存层无需修改Service

#### 2. 事务管理模式

**实现**（追溯SAD §2.1 关键决策2）：

- Service层方法使用 `@Transactional`注解
- 数据库操作在同一事务中执行，保证原子性
- 异常自动回滚（如任务创建失败，历史记录也回滚）

**示例场景**：

```java
@Service
public class TaskService {
    @Transactional(rollbackFor = Exception.class)
    public Task createTask(CreateTaskRequest request) {
        Task task = taskMapper.insert(buildTask(request)); // 1. 插入任务
        taskHistoryMapper.insert(buildHistory(task)); // 2. 插入历史记录
        if (task.getAssigneeId() != null) {
            notificationService.notifyAssignment(task); // 3. 异步通知
        }
        return task;
    }
}
```

#### 3. 异步通知模式

**实现**（追溯SAD §2.1 关键决策5）：

- `NotificationService`使用 `@Async`注解
- 通知发送在独立线程池执行，不阻塞主业务
- 日志写入失败不影响任务创建成功

**架构体现**：

```
TaskService.createTask()
  ├─ taskMapper.insert() [事务内]
  ├─ taskHistoryMapper.insert() [事务内]
  └─ notificationService.notifyAssignment() [异步，事务外]
```

#### 4. JWT无状态认证模式

**实现**：

- 用户登录成功后生成JWT Token（30分钟有效期）
- 前端每次请求携带Token（`Authorization: Bearer <token>`）
- `JwtFilter`拦截所有API请求，验证Token有效性
- 无需Session存储，支持水平扩展

### 组件依赖规则

| 依赖方向              | 允许 | 禁止              | 原因                                               |
| --------------------- | ---- | ----------------- | -------------------------------------------------- |
| Controller → Service | ✅   | -                 | Controller调用Service执行业务逻辑                  |
| Service → Mapper     | ✅   | -                 | Service调用Mapper访问数据库                        |
| Service → Service    | ✅   | ⚠️ 避免循环依赖 | 跨模块调用（如TaskService调用NotificationService） |
| Mapper → Service     | ❌   | ✅                | 违反分层原则，Mapper不应包含业务逻辑               |
| Controller → Mapper  | ❌   | ✅                | 跨层调用，绕过Service事务管理                      |

### 性能优化点

| 优化措施                       | 实施位置             | 预期效果                        | 追溯来源            |
| ------------------------------ | -------------------- | ------------------------------- | ------------------- |
| **数据库索引**           | task_mapper          | 查询时间从500ms降至<100ms       | SAD §3.1 性能要求  |

1. 安装插件：`PlantUML` (by jebbs)

3. 按 `Alt + D`预览渲染结果


## 架构演进规划

### V1.0（当前MVP）

- ✅ Context图：3个用户角色，1个核心系统，无外部依赖
- ✅ Container图：5个容器（前端、Nginx、后端、数据库、备份）
- ✅ Component图：20个组件（Controller 7个、Service 5个、Mapper 4个、Security 2个）

### V2.0（未来演进）

**新增外部依赖**（更新Context图）：

- 企业微信API（实时通知推送）
- Elasticsearch（全文搜索优化）

**新增容器**（更新Container图）：

- Redis缓存服务（缓存任务列表、用户信息）
- WebSocket服务（实时通知，替代HTTP轮询）

**新增组件**（更新Component图）：

- `WorklogService`：工时统计服务
- `GanttController`：甘特图视图控制器
- `DependencyService`：任务依赖关系管理
