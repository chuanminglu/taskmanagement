> **📚 参考标准**：ISO/IEC 25010质量模型、架构评审最佳实践

## 🎯 G - 目标与意图

### 核心目标

生成**全面覆盖、针对性强、可判定**的架构评审Checklist，确保架构设计质量，降低技术风险，支撑技术决策。

### 具体目标

1. **全面性**：覆盖技术可行性、数据设计、API设计、性能、安全、可扩展性、风险应对等8大维度
2. **针对性**：基于具体项目的技术栈和设计文档，生成定制化检查项
3. **可判定性**：每条检查项可明确判定为✅通过/⚠️待改进/❌不通过
4. **可执行性**：不通过项有明确的整改建议和优先级

### 业务价值

- **为评审委员会**：提供结构化评审依据，提高评审效率和质量
- **为设计人员**：提供设计自检清单，减少评审返工次数
- **为项目经理**：提供风险识别工具，支持风险管理决策
- **为技术演进**：沉淀技术债务，支持系统持续改进

### 成功标准

- ✅ Checklist覆盖8大核心评审维度
- ✅ 检查项总数10-15条（避免过于繁琐）
- ✅ 每条检查项可明确判定（✅/⚠️/❌）
- ✅ 不通过项有整改建议和优先级（P0/P1/P2）
- ✅ 包含风险矩阵和评审报告模板

```markdown
| **被评审文档** | {ADR-001、Schema设计、API契约设计等} |

## 🎯 评审目标

{简要说明本次评审的核心目标，1-2句话}

## 📊 评审维度

本Checklist覆盖以下8大维度：

1. ✅ 技术可行性
2. ✅ 数据设计合理性
3. ✅ 组件划分与接口设计
4. ✅ API设计规范性
5. ✅ 性能与可扩展性
6. ✅ 安全性与合规性
7. ✅ 可观测性与运维
8. ✅ 风险应对与回滚方案

## 📝 使用说明

- **评审流程**：
  1. 评审前：设计人员自检（修正明显问题）
  2. 评审中：评审委员逐项评审（标注✅/⚠️/❌）
  3. 评审后：汇总问题清单，制定整改计划

- **评分标准**：
  - ✅ **通过**：符合标准，无需整改
  - ⚠️ **待改进**：存在优化空间，建议改进（P1/P2优先级）
  - ❌ **不通过**：存在严重问题，必须整改（P0优先级）

- **通过条件**：
  - 无❌不通过项
  - ⚠️待改进项不超过3个
  - 所有P0问题有整改计划
```

**8大维度的检查项示例**：

#### 2️⃣ 数据设计合理性

- [ ] **Schema完整性**：4张表（systems、requirements、conversations、recommendations）是否覆盖所有核心业务流程？
- [ ] **关系设计**：外键关系是否正确？（如conversations.requirement_id → requirements.id）
- [ ] **索引设计**：高频查询字段是否建立索引？（如requirements.user_id、conversations.requirement_id）
- [ ] **扩展性**：是否预留扩展字段？（如metadata JSON字段）

#### 3️⃣ 组件划分与接口设计

- [ ] **前后端分离**：前后端职责是否清晰？是否有API契约文档？
- [ ] **组件内聚性**：前端组件是否高内聚低耦合？（如RecommendationCard、ConversationPanel独立复用）
- [ ] **接口完整性**：API是否覆盖所有前端功能？是否有遗漏的接口？

#### 4️⃣ API设计规范性

- [ ] **RESTful规范**：API是否符合RESTful设计原则？（资源导向、HTTP方法语义正确）
- [ ] **响应格式统一**：是否使用统一的响应格式 `{code, message, data}`？
- [ ] **错误处理**：是否定义了完整的错误码和错误消息？
- [ ] **文档完整性**：是否有OpenAPI文档？是否可导入Swagger UI测试？

#### 5️⃣ 性能与可扩展性

- [ ] **数据库性能**：SQLite是否能支持预期的并发量？（QPS预估）
- [ ] **LLM调用性能**：DeepSeek API延迟是否可接受？（P95<3秒？）
- [ ] **缓存策略**：是否有缓存设计？（如系统列表缓存、推荐结果缓存）
- [ ] **水平扩展**：未来用户量增长时，是否可平滑迁移到PostgreSQL/MySQL？

#### 6️⃣ 安全性与合规性

- [ ] **API Key管理**：DeepSeek API Key是否安全存储？（环境变量或密钥管理服务）
- [ ] **数据加密**：敏感数据是否加密存储？（如用户需求描述）
- [ ] **鉴权机制**：API是否有鉴权机制？（JWT Token或其他）
- [ ] **日志脱敏**：日志中是否脱敏敏感信息？（如API Key、用户ID）

#### 7️⃣ 可观测性与运维

- [ ] **日志规范**：是否定义了日志级别和日志格式？（如JSON格式日志）
- [ ] **监控指标**：是否定义了关键监控指标？（如API调用量、成功率、延迟）
- [ ] **告警策略**：是否定义了告警阈值和通知方式？
- [ ] **部署文档**：是否有部署文档和运维手册？

#### 8️⃣ 风险应对与回滚方案

- [ ] **风险识别**：ADR中是否识别了所有关键风险？（如API限流、数据库性能）
- [ ] **回滚条件**：是否定义了明确的回滚条件？（如准确率<80%、延迟P95>5秒）
- [ ] **备选方案**：是否有备选方案？（如大模型切换、部署架构调整）
- [ ] **回滚计划**：是否有具体的回滚执行计划？（步骤、预计时间）

### 2. 质量要求

#### 针对性（强制）

- ✅ 检查项必须基于具体的设计文档（ADR、Schema、API契约）
- ✅ 检查项必须标注来源（如"来自ADR-001 §候选方案"）
- ✅ 检查项必须与项目的技术栈和业务场景相关（不能是通用模板）

#### 可判定性（强制）

- ✅ 每条检查项可明确判定为✅/⚠️/❌
- ✅ 避免主观表达（如"设计是否合理"），改为具体问题（如"4张表是否覆盖所有业务流程"）
- ✅ 评审要点提供3-5个具体检查点

#### 完整性（强制）

- ✅ 覆盖8大核心维度（技术可行性、数据设计、API设计、性能、安全、可观测性、风险应对等）
- ✅ 每个维度2-3条检查项（总数10-15条）
- ✅ 包含风险矩阵和评审报告模板

#### 可执行性（强制）

- ✅ 不通过项有明确的整改建议
- ✅ 整改建议有责任人和截止日期
- ✅ 整改建议有优先级（P0/P1/P2）

### 3. 格式规范

- **文档格式**：Markdown
- **Checkbox**：使用 `- [ ]`格式（评审时可勾选）
- **表格**：用于结构化信息（如风险矩阵、评审报告）
- **emoji**：增强可读性（✅通过 ⚠️待改进 ❌不通过 🚨风险 📋检查项）

### 4. 特别说明

#### 评审重点优先级

根据项目阶段调整评审重点：

| 项目阶段               | 评审重点                         |
| ---------------------- | -------------------------------- |
| **概要设计阶段** | 技术可行性、架构合理性、风险识别 |
| **详细设计阶段** | 数据设计、API设计、性能与安全    |
| **开发阶段**     | 代码质量、接口实现、测试覆盖     |
| **上线前**       | 可观测性、运维文档、回滚方案     |

#### 信息不足的处理

如果架构设计文档缺少某些信息，你应该：

1. **标注为待补充项**：在检查项中标注 `【待补充】`

   - 示例：`- [ ] 【待补充】是否有API压测数据？（设计文档中未提及）`
2. **列入评审问题**：在评审报告的"P1问题"中列出

   - 示例："缺少性能压测数据，无法评估系统承载能力"
3. **提供补充建议**：在整改建议中说明需补充的内容

   - 示例："补充API压测数据（预期QPS、延迟P95、并发用户数）"

### 5. 输出格式

直接输出完整的架构评审Checklist，包含：

1. 评审元信息（项目名称、评审日期、评审人、使用说明）
2. Checklist主体（8大维度、10-15条检查项）
3. 风险矩阵（汇总风险、应对措施、责任人）
4. 评审报告模板（评审结论、问题汇总、签字、下一步行动）

不要有任何前言或解释。
