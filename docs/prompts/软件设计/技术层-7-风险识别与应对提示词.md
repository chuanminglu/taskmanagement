> **📌 用途**：基于架构设计文档，识别技术风险并制定应对措施

## 🎯 G - 目标与意图

### 核心目标

**全面识别**技术风险，**量化评估**风险等级，**制定可执行**的应对措施，确保项目按时交付且质量可控。

### 具体目标

1. **全面性**：覆盖技术可行性、性能、安全、依赖、团队能力、时间等6大风险类别
2. **量化性**：使用概率×影响矩阵量化风险等级（高/中/低）
3. **可执行性**：每个风险有明确的应对措施、责任人、检查点
4. **前瞻性**：识别潜在风险（如未来扩展性问题），而非仅当前风险

### 业务价值

- **为项目经理**：提供风险清单，支持项目计划调整和资源分配
- **为架构师**：识别技术债务，制定技术演进路线图
- **为开发团队**：明确风险应对责任，减少突发问题的影响
- **为管理层**：提供风险可视化，支持Go/No-Go决策

### 成功标准

- ✅ 识别8-12个关键技术风险（覆盖6大类别）
- ✅ 每个风险有量化的概率、影响、风险等级
- ✅ 高风险（🔴）必须有缓解措施和监控机制
- ✅ 每个风险有责任人和检查点（何时复查）
- ✅ 包含风险矩阵可视化和应急预案

```markdown
本方案覆盖以下6大风险类别：

| 类别 | 说明 | 典型风险 |
|------|------|---------|
| **技术可行性风险** | 技术选型是否成熟、可用 | API不稳定、新技术学习曲线高 |

## 📝 风险评估方法

### 风险等级计算公式

```

风险等级 = 发生概率 × 影响程度

```

**发生概率**：
- **高**：>50%，很可能发生
- **中**：20%-50%，有一定可能发生
- **低**：<20%，不太可能发生

**影响程度**：
- **高**：导致项目失败、严重延期（>50%）、核心功能不可用
- **中**：导致项目延期（20%-50%）、部分功能受影响
- **低**：对项目影响较小，可接受

**风险等级矩阵**：

| 概率\影响 | 低影响 | 中影响 | 高影响 |
|----------|--------|--------|--------|
| **高概率** | 🟡 中 | 🔴 高 | 🔴 高 |
| **中概率** | 🟢 低 | 🟡 中 | 🔴 高 |
| **低概率** | 🟢 低 | 🟢 低 | 🟡 中 |

**风险应对策略**：
- 🔴 **高风险**：必须制定缓解措施，持续监控
- 🟡 **中风险**：制定应对计划，定期复查
- 🟢 **低风险**：接受风险，监控即可
```

```markdown
### 风险详细分析

#### 类别1：技术可行性风险

##### 🔴 R1：DeepSeek API不稳定或服务中断

**风险描述**：
DeepSeek API是外部第三方服务，可能存在：
- 服务不稳定（偶发性502/503错误）
- API限流（QPM/QPD超限）
- 服务中断（维护或故障）
- API接口变更（破坏性更新）

**发生概率**：中（30%）
- DeepSeek是新兴服务商，稳定性尚未经过大规模验证
- 项目原型阶段调用量不大，触发限流概率中等

**影响程度**：高
- 核心推荐功能完全依赖DeepSeek API
- 如果API不可用，系统无法提供推荐服务
- 影响项目演示和验收

**风险等级**：🔴 高（中概率 × 高影响）

**应对措施**：

1. **缓解措施（降低概率）**：
   - 实现API调用重试机制（最多3次，指数退避）
   - 实现请求队列和限流控制（避免触发API限流）
   - 监控API调用成功率和延迟（设置告警阈值）

2. **应急预案（降低影响）**：
   - 准备备选方案：Qwen API（阿里云）或ChatGPT API
   - 实现LLM适配器模式（统一接口，快速切换）
   - 准备切换SOP（操作手册），预计1天内完成切换
   - 准备降级方案：基于规则的关键词匹配推荐

3. **监控与检查点**：
   - 开发阶段：每日监控API调用成功率（目标≥95%）
   - 上线前：进行API压测（模拟100次并发调用）
   - 运营阶段：实时监控API状态，成功率<90%触发告警

**责任人**：架构师
**检查点**：开发第2天完成备选方案集成测试

---

##### 🟡 R2：浏览器插件兼容性问题

**风险描述**：
浏览器插件开发涉及：
- Chrome版本兼容性（Manifest V3 vs V2）
- 不同浏览器兼容性（Chrome、Edge、Firefox）
- 浏览器安全策略限制（CSP、CORS）

**发生概率**：低（15%）
- 项目只支持Chrome，范围可控
- Vue 3 + Vite生态成熟，插件开发脚手架完善

**影响程度**：中
- 影响用户使用体验，但不影响核心功能
- 可通过降级到Web应用解决

**风险等级**：🟡 中（低概率 × 中影响）

**应对措施**：

1. **规避措施**：
   - V1版本只支持Chrome浏览器（最新3个版本）
   - 明确告知用户系统要求

2. **缓解措施**：
   - 使用成熟的插件开发框架（如Plasmo、WXT）
   - 开发阶段在多个Chrome版本测试

3. **后续计划**：
   - V2版本考虑支持Edge（基于Chromium，兼容性好）
   - 如果插件问题严重，可降级为Web应用

**责任人**：前端负责人
**检查点**：开发第1天完成插件基础框架验证

---

#### 类别2：性能风险

##### 🔴 R3：推荐响应时间超过3秒（P95）

**风险描述**：
推荐服务的响应时间受以下因素影响：
- DeepSeek API调用延迟（通常1-2秒，但P95可能>3秒）
- 数据库查询延迟（SQLite性能有限）
- Prompt长度（过长导致推理时间增加）

**发生概率**：中（40%）
- DeepSeek API延迟波动较大
- 初期Prompt未优化，可能较长

**影响程度**：中
- 用户体验下降，但不影响功能可用性
- 不符合性能指标（P95<3秒）

**风险等级**：🔴 高（中概率 × 中影响，但涉及用户体验，升级为高）

**应对措施**：

1. **缓解措施（降低延迟）**：
   - 优化Prompt长度（控制在500 tokens以内）
   - 实现系统信息缓存（减少数据库查询）
   - 使用异步处理（前端显示加载动画，提升感知性能）

2. **降级措施**：
   - 设置超时时间（5秒），超时返回默认推荐
   - 提供"正在思考中"的友好提示

3. **监控与优化**：
   - 记录每次API调用的延迟（P50/P95/P99）
   - 如果P95持续>3秒，考虑切换到更快的模型

**责任人**：AI工程师
**检查点**：开发第2天完成性能压测，验证P95延迟

---

##### 🟢 R4：SQLite并发性能不足

**风险描述**：
SQLite是单文件数据库，并发写入能力有限：
- 写入时会锁表，影响读取性能
- 高并发场景可能导致"database is locked"错误

**发生概率**：低（10%）
- 原型阶段并发用户数≤10人
- 主要是读操作，写入频率低

**影响程度**：低
- 仅影响高并发场景，原型阶段可接受
- 后续可平滑迁移到PostgreSQL

**风险等级**：🟢 低（低概率 × 低影响）

**应对措施**：

1. **接受风险**：
   - 原型阶段并发量小，SQLite性能足够
   - 暂不处理，监控即可

2. **后续计划**：
   - V2版本（用户量>50人）迁移到PostgreSQL
   - 准备数据迁移脚本（SQLite → PostgreSQL）

**责任人**：后端负责人
**检查点**：开发第3天完成并发测试（10用户同时访问）

#### 类别3：依赖风险

##### 🔴 R5：推荐准确率低于70%

**风险描述**：
推荐准确率受以下因素影响：
- Prompt设计不合理（未提供足够上下文）
- 训练样本不足（系统信息不完整）
- 需求描述模糊（用户输入质量低）

**发生概率**：中（35%）
- 项目团队LLM应用经验有限
- Prompt工程需要反复调优

**影响程度**：高
- 低于70%无法通过验收标准
- 影响用户信任度和使用意愿

**风险等级**：🔴 高（中概率 × 高影响）

**应对措施**：

1. **缓解措施（提升准确率）**：
   - 使用Few-Shot Learning（提供3-5个标注样本）
   - 优化Prompt结构（明确角色、任务、输出格式）
   - 补充完整的系统信息（至少30个系统）
   - 实现需求澄清对话（引导用户补充信息）

2. **验证与迭代**：
   - 准备20个测试用例（覆盖常见需求场景）
   - 每日测试准确率，低于70%立即优化Prompt
   - 收集真实用户反馈，持续优化

3. **降级方案**：
   - 如果LLM推荐效果差，降级为关键词匹配推荐
   - 提供"不满意？换一批推荐"功能

**责任人**：AI工程师
**检查点**：开发第2天完成Prompt初步优化，准确率≥60%；第3天达到≥70%

#### 类别4：安全与合规风险

##### 🟡 R6：DeepSeek API Key泄露

**风险描述**：
API Key如果泄露，可能导致：
- 被恶意调用，消耗配额（费用损失）
- 敏感数据泄露（如需求描述）

**发生概率**：低（20%）
- 开发阶段容易误提交到代码库
- 本地运行，暴露风险较低

**影响程度**：中
- 费用损失可控（DeepSeek成本低）
- 敏感数据泄露影响用户信任

**风险等级**：🟡 中（低概率 × 中影响）

**应对措施**：

1. **预防措施**：
   - API Key存储在环境变量（`.env`文件，添加到`.gitignore`）
   - 使用密钥管理工具（如HashiCorp Vault，V2版本考虑）
   - 代码审查检查API Key是否硬编码

2. **检测措施**：
   - 使用Git Hooks检测敏感信息提交
   - 定期检查API Key使用量（异常调用触发告警）

3. **应急措施**：
   - 如果API Key泄露，立即重置（DeepSeek支持在线重置）
   - 准备备用API Key

**责任人**：后端负责人
**检查点**：开发第1天完成API Key安全存储配置

---

##### 🟢 R7：用户需求数据未加密

**风险描述**：
用户提交的需求描述可能包含敏感信息（如人员姓名、部门），存储在SQLite中未加密。

**发生概率**：低（10%）
- 本地运行，数据库文件仅本地访问
- 原型阶段未涉及生产数据

**影响程度**：低
- 原型阶段数据为测试数据，无敏感性
- 后续生产环境需加密

**风险等级**：🟢 低（低概率 × 低影响）

**应对措施**：

1. **接受风险**：
   - 原型阶段不处理，后续V2版本加密

2. **后续计划**：
   - 生产环境使用字段级加密（AES-256）
   - 敏感字段脱敏（如姓名替换为工号）

**责任人**：后端负责人
**检查点**：V2版本设计阶段评估加密方案

#### 类别5：团队能力风险

##### 🟡 R8：LLM应用开发经验不足

**风险描述**：
团队对LLM应用开发（Prompt工程、Few-Shot Learning）经验有限，可能导致：
- Prompt设计不合理，准确率低
- 调试困难，问题定位慢
- 开发效率低于预期

**发生概率**：中（40%）
- 团队首次开发LLM应用
- Prompt工程需要反复试错

**影响程度**：中
- 影响开发进度和质量
- 可能导致延期1-2天

**风险等级**：🟡 中（中概率 × 中影响）

**应对措施**：

1. **能力提升**：
   - 开发前进行1天技术培训（Prompt工程最佳实践）
   - 参考DeepSeek官方示例和社区最佳实践
   - 使用LangChain等框架简化开发

2. **降低难度**：
   - 使用Few-Shot Learning（减少Prompt调优难度）
   - 复用成熟的Prompt模板

3. **外部支持**：
   - 如遇到技术难题，寻求DeepSeek技术支持

**责任人**：AI工程师
**检查点**：开发第1天完成技术培训，输出Prompt设计规范

##### 🟢 R9：关键人员请假或离职

**风险描述**：
3人小团队，任何1人缺席都会影响项目进度。

**发生概率**：低（10%）
- 项目周期仅3天，请假概率低

**影响程度**：中
- 影响开发进度，可能延期1天

**风险等级**：🟢 低（低概率 × 中影响）

**应对措施**：

1. **预防措施**：
   - 项目启动前确认团队成员时间可用性
   - 代码实时同步到Git，任何人可接手

2. **应急措施**：
   - 如有人缺席，调整任务优先级（聚焦核心功能）
   - 延期1天，调整演示时间

**责任人**：项目经理
**检查点**：每日站会确认团队状态

#### 类别6：时间与资源风险

##### 🔴 R10：3天开发周期延期

**风险描述**：
3天开发周期紧张，可能因以下原因延期：
- 功能范围过大（需求蔓延）
- 技术难题（如Prompt调优耗时）
- 环境搭建问题

**发生概率**：中（30%）
- 首次开发LLM应用，存在不确定性
- 时间缓冲不足

**影响程度**：高
- 影响项目演示和验收
- 影响后续项目规划

**风险等级**：🔴 高（中概率 × 高影响）

**应对措施**：

1. **范围控制**：
   - 明确V1版本MVP范围（仅3个核心功能）
   - 推迟次要功能到V2（如需求质量检测）
   - 使用MoSCoW优先级（Must/Should/Could/Won't）

2. **进度管理**：
   - 每日站会跟踪进度（燃尽图）
   - 第2天中午复查进度，如落后立即砍功能
   - 预留半天缓冲时间（用于集成测试和Bug修复）

3. **应急方案**：
   - 如确实无法按时完成，延期1天并调整演示时间
   - 演示使用Mock数据（降低对真实API的依赖）

**责任人**：项目经理
**检查点**：每日17:00进度复查，第2天中午关键检查点

---

##### 🟡 R11：预算超支（API调用费用）

**风险描述**：
DeepSeek API按Token计费，可能因以下原因超支：
- Prompt过长（输入Token多）
- 测试频繁（重复调用）
- 未设置配额限制

**发生概率**：低（15%）
- DeepSeek成本低（约0.001元/1K tokens）
- 原型阶段调用量不大

**影响程度**：低
- 预算上限100元/月，超支风险小
- 即使超支，金额可控

**风险等级**：🟡 中（低概率 × 低影响，但涉及成本控制，升级为中）

**应对措施**：

1. **成本控制**：
   - 优化Prompt长度（控制输入Token）
   - 实现缓存机制（相同需求不重复调用）
   - 设置API调用配额（如每天最多1000次）

2. **监控**：
   - 每日监控API调用量和费用
   - 设置告警（费用>50元触发提醒）

**责任人**：后端负责人
**检查点**：开发第2天检查累计费用
```

### 2. 质量要求

#### 全面性（强制）

- ✅ 覆盖6大风险类别（技术可行性、性能、依赖、安全、团队能力、时间资源）
- ✅ 每个类别至少识别1-2个风险
- ✅ 识别风险总数8-12个（不要遗漏关键风险，也不要过于琐碎）

#### 量化性（强制）

- ✅ 每个风险有明确的概率（高/中/低）和影响（高/中/低）
- ✅ 使用概率×影响矩阵计算风险等级（🔴高/🟡中/🟢低）
- ✅ 避免主观判断，说明概率和影响的判断依据

#### 可执行性（强制）

- ✅ 高风险（🔴）必须有缓解措施和应急预案
- ✅ 每个风险有明确的责任人和检查点
- ✅ 应对措施具体可执行（不是"加强管理"这种虚词）
- ✅ 检查点有明确的时间（如"第2天17:00"）

#### 针对性（强制）

- ✅ 风险基于具体的架构设计和项目约束（不是通用模板）
- ✅ 风险描述具体（如"DeepSeek API不稳定"而非"第三方依赖风险"）
- ✅ 应对措施针对该项目（如"切换到Qwen"而非"准备备选方案"）

- **emoji**：增强可读性（🔴高风险 🟡中风险 🟢低风险 ⚫⚪🔵矩阵图标）
- **颜色编码**：风险等级使用红/黄/绿区分

### 4. 特别说明

#### 风险识别的常见误区

| 误区                             | 说明                         | 正确做法                   |
| -------------------------------- | ---------------------------- | -------------------------- |
| **只关注技术风险**         | 忽略团队能力、时间、资源风险 | 覆盖6大类别                |
| **风险描述过于笼统**       | 如"系统性能不足"             | 具体化，如"API延迟P95>3秒" |
| **只识别风险，不制定应对** | 列出一堆风险，没有缓解措施   | 每个高风险必须有应对措施   |
| **应对措施不可执行**       | 如"加强管理""提高质量"       | 具体措施，如"实现重试机制" |
| **没有责任人和检查点**     | 风险无人跟踪，成为空谈       | 明确责任人和复查时间       |

#### 风险应对策略选择

| 策略                       | 适用场景             | 示例                       |
| -------------------------- | -------------------- | -------------------------- |
| **规避（Avoid）**    | 完全消除风险         | 不使用不稳定的新技术       |
| **缓解（Mitigate）** | 降低概率或影响       | 实现API重试机制            |
| **转移（Transfer）** | 将风险转移给第三方   | 购买商业技术支持服务       |
| **接受（Accept）**   | 风险等级低，监控即可 | 原型阶段接受SQLite性能限制 |

#### 信息不足的处理

如果架构设计文档缺少某些信息，你应该：

1. **基于经验推断**：参考类似项目的常见风险

   - 示例：所有LLM项目都存在准确率风险
2. **标注为待确认**：在风险描述中标注

   - 示例：`【待确认】团队对Vue 3的熟悉程度？`
3. **建议补充信息**：在输出末尾列出待补充事项

   - 示例："建议补充：团队技术栈能力评估报告"

---

### 5. 输出格式

直接输出完整的风险识别与应对方案，包含：

1. 风险管理概述（目标、分类框架、评估方法）
2. 风险清单（详细分析+汇总表）
3. 风险矩阵可视化（概率×影响矩阵+热力图）
4. 风险监控与应急预案（监控指标+复查计划+应急预案）

不要有任何前言或解释。


**📌 注意事项**：

1. 风险管理是持续过程，不是一次性活动（定期复查、更新风险清单）
2. 高风险（🔴）必须制定缓解措施，不能仅靠"加强监控"
3. 应急预案必须提前准备，不能等风险发生才临时处理
4. 风险责任人必须明确，避免"人人负责=无人负责"
5. 建议使用风险管理工具（如Jira、Trello）跟踪风险状态
6. 项目复盘时，评估风险识别的准确性，持续优化风险管理能力
