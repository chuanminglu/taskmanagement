# Product Backlog梳理 - GeekBooks示例输入

> **📌 场景说明**: GeekBooks极客书店Sprint 3计划实现智能推荐功能
>
> **项目背景**: 在线技术书店，50万+注册用户，15,000+ SKU，目前首页推荐采用人工运营配置，效率低且转化率不高

---

## 输入材料1：用户故事列表

### 用户故事 #1：智能图书推荐

**作为** 注册用户  
**我希望** 在首页看到根据我的浏览和购买历史推荐的图书  
**以便** 我能快速发现感兴趣的新书，而不用自己搜索

**业务价值**: 
- 提升首页停留时长从45秒到90秒（100%提升）
- 推荐点击率≥30%（行业基准15%）
- GMV提升10-15%（预计月增50万）

**验收标准**：
- [ ] 首页展示"为你推荐"模块，展示6-8本图书
- [ ] 推荐基于用户浏览历史（最近30天）和购买记录
- [ ] 推荐响应时间P95<1秒
- [ ] 推荐点击率≥30%（需A/B测试验证）
- [ ] 支持降级：新用户或数据不足时展示热门图书

**技术约束**：
- 推荐算法：协同过滤（User-based CF）
- 算法复杂度：O(n) n=用户浏览记录数，需优化到<100ms
- 缓存策略：Redis缓存30分钟，用户行为变化后刷新
- 降级方案：推荐服务不可用时展示热门图书（99.5%可用率）

---

### 用户故事 #2：新用户冷启动推荐

**作为** 新注册用户（无浏览和购买历史）  
**我希望** 在首页看到热门/精选图书推荐  
**以便** 我能快速了解平台的图书品类和热门图书

**业务价值**: 
- 降低新用户流失率（从60%降低到45%）
- 提升新用户首单转化率（从5%提升到8%）

**验收标准**：
- [ ] 新用户（注册<7天且无购买记录）首页展示"热门推荐"模块
- [ ] 推荐基于全站热销榜（最近7天销量Top 50）
- [ ] 支持按品类筛选（编程、算法、AI、架构、前端）
- [ ] 用户点击品类后，推荐更新为该品类的热门图书

**技术约束**：
- 热门榜单数据源：从订单表聚合，每小时更新一次
- 品类数据：从图书表关联查询（book.category字段）
- 缓存策略：全站热销榜缓存1小时

---

### 用户故事 #3：热门榜单管理后台

**作为** 运营人员  
**我希望** 在后台管理系统查看和调整热门榜单  
**以便** 我能手动干预榜单（如剔除违规图书、置顶运营活动图书）

**业务价值**: 
- 确保榜单质量（剔除刷单、违规图书）
- 支持运营活动（如新书首发、促销活动）

**验收标准**：
- [ ] 后台展示当前热门榜单（最近7天Top 50）
- [ ] 支持手动置顶图书（最多5本）
- [ ] 支持手动屏蔽图书（如违规图书）
- [ ] 榜单调整后立即生效（清空缓存）
- [ ] 记录操作日志（谁在什么时间做了什么操作）

**技术约束**：
- 榜单数据存储：MySQL（hot_books表）
- 手动调整数据：Redis缓存（manual_top_books, blocked_books）
- 操作日志：写入audit_log表

---

### 用户故事 #4：推荐效果反馈

**作为** 注册用户  
**我希望** 对推荐的图书进行"感兴趣"或"不感兴趣"反馈  
**以便** 系统能更准确地了解我的偏好，优化推荐结果

**业务价值**: 
- 提升推荐准确率（从70%提升到85%）
- 增强用户参与感（用户感觉推荐是"为我定制的"）

**验收标准**：
- [ ] 每本推荐图书下方有"👍 感兴趣"和"👎 不感兴趣"按钮
- [ ] 用户点击后，推荐立即刷新（移除该书，补充新推荐）
- [ ] 反馈数据写入用户行为日志（user_feedback表）
- [ ] 反馈数据用于后续推荐优化（下次推荐考虑反馈）

**技术约束**：
- 反馈数据异步写入（Kafka + Flink实时计算）
- 推荐刷新：调用推荐服务API，排除已反馈图书
- 反馈权重：👎 不感兴趣权重 × 2（降低该类图书推荐概率）

**依赖关系**：
- ⚠️ 依赖US-001（智能图书推荐）：需要推荐服务API支持排除图书功能

---

### 用户故事 #5：推荐位管理（运营配置）

**作为** 运营人员  
**我希望** 在后台配置首页推荐位的展示逻辑（智能推荐 vs 运营推荐）  
**以便** 我能灵活控制推荐内容（如促销活动时展示活动图书）

**业务价值**: 
- 支持运营活动灵活配置（如双11、新书首发）
- 平衡算法推荐和运营需求（算法70% + 运营30%）

**验收标准**：
- [ ] 后台配置推荐位策略（100%智能推荐 / 70%智能+30%运营）
- [ ] 运营推荐位支持手动选择图书（最多10本）
- [ ] 配置后立即生效（清空缓存）
- [ ] 支持按时间段配置（如双11期间使用特殊配置）

**技术约束**：
- 配置数据存储：MySQL（recommend_config表）
- 配置缓存：Redis（config:recommend_strategy）
- 配置更新：发布配置变更事件到Kafka，推荐服务监听

## 输入材料2：团队与约束信息

### 团队信息

**团队规模**：
- 后端工程师：3人（Spring Boot）
- 前端工程师：3人（Vue 3）
- 测试工程师：1人（功能测试 + 自动化测试）
- DevOps工程师：1人（CI/CD + 监控）
- **合计**：8人

**Sprint长度**：2周（10个工作日）

**团队产能**：
- 每人每天有效工时：6小时（扣除会议、答疑、杂事）
- 团队总工时：8人 × 10天 × 6小时 = 480小时
- 团队速度（Velocity）：上Sprint完成40 Story Points

**团队能力画像**：
- 推荐算法经验：❌ 无（团队首次做推荐功能）
- 微服务开发经验：✅ 有（上Sprint做过支付微服务）
- Vue 3开发经验：✅ 熟练
- Kafka实时计算：✅ 有（但不熟练，需要支持）

---

### 技术约束

**技术栈**：
- 后端：Spring Boot 3.x + MyBatis-Plus
- 前端：Vue 3 + Element Plus
- 数据库：MySQL 8.0
- 缓存：Redis 7.x
- 消息队列：Kafka 3.x
- 实时计算：Flink 1.15
- 部署：Kubernetes + Docker

**架构约束**：
- 推荐服务：新建独立微服务（recommend-service）
- 推荐服务API：RESTful，响应时间P95<1秒
- 推荐算法：协同过滤（User-based CF），不使用深度学习（团队无经验）
- 外部依赖：无（自研算法，不调用外部AI服务）

**性能要求**：
- 推荐服务QPS：≥1000（支撑首页高峰流量）
- 推荐响应时间：P95<1秒，P99<3秒
- 推荐服务可用率：99.5%（降级到热门推荐）

**安全要求**：
- 用户行为数据脱敏（不记录敏感信息如手机号）
- 推荐算法防作弊（识别刷单、批量注册用户）

---

### 业务约束

**业务目标**（CEO要求）：
- 本Sprint必须完成智能推荐核心功能（US-001 + US-002）
- Sprint末需向CEO Demo（展示推荐效果）

**运营要求**：
- 运营团队希望保留人工干预能力（US-003热门榜单管理）
- 双11临近（下个Sprint），需要推荐位支持运营配置（US-005）

**风险容忍度**：
- 推荐准确率不强制（初版70%即可，后续迭代优化）
- 推荐算法可简化（如用热度+品类代替协同过滤）
- 但推荐功能必须上线（业务承诺）

---

### 已知风险

1. **技术风险**：协同过滤算法实现复杂度高，团队无经验
   - 可能导致开发延期或算法效果不佳
2. **依赖风险**：US-004（推荐反馈）依赖US-001的API，可能被阻塞
3. **数据风险**：热门榜单数据质量未验证（可能有刷单数据）
4. **时间风险**：Sprint只有2周，5个用户故事工作量可能超产能
