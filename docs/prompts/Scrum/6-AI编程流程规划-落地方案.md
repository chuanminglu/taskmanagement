## 🎯 阶段1：准备期（1-2周）

### Week 1：工具链搭建 + 团队培训

#### Day 1-2：Prompt工程培训

**培训目标**：让团队成员能独立编写达到70%首次成功率的Prompt

**Day 1上午（2h）：理论培训**

```markdown
培训议程：

1. 什么是Subagent？与普通AI对话的区别（30min）
   - 普通对话：探索性，多轮交互
   - Subagent：任务式，一次性输出，类似API调用
   
2. 好Prompt的6个要素（30min）
   - 背景：让AI理解任务上下文
   - 目标：明确产出（不要让AI猜）
   - 输入：提供参考文件路径
   - 输出：列出所有需要创建的文件
   - 约束：说清楚不能做什么
   - 验收：可执行的验证命令
   
3. 常见失败原因（30min）
   - 上下文不足（AI不知道已有哪些代码）
   - 约束不清（AI修改了不该修改的文件）
   - 验收模糊（AI不知道什么是"完成"）
   
4. 工具使用指引（30min）
   - 如何让AI读取现有代码（@文件引用 or read_file）
   - 如何让AI执行验证命令
   - 如何判断AI输出是否可用
```

**Day 1下午（3h）：实践练习**

每人完成以下练习：

```markdown
练习1：为以下伪任务编写Prompt（30min）
  任务：创建UserController的REST API
  参考代码：ProductController.java
  目标：生成CRUD接口
  
练习2：互相评审练习1的Prompt（30min）
  评审标准：检查6要素是否完整
  
练习3：执行自己的Prompt，观察AI输出（1h）
  记录：首次成功率、需要几轮迭代
  
练习4：分享失败经验（1h）
  每人分享1个Prompt失败案例及改进方法
```

### Week 2：回顾决策

**Week 2 Team Retrospective**（1小时）

议题：
1. **数据回顾**（15min）：展示试点任务的实际数据
2. **问题分析**（20min）：遇到哪些问题？原因是什么？
3. **决策**（10min）：是否进入扩展期？
4. **行动计划**（15min）：下个Sprint的调整策略

**决策树**：

```
试点任务是否成功？
├─ 成功（Review通过，效率提升≥0）
│   └─ 团队愿意继续？
│       ├─ 是 → ✅ 进入阶段2（扩展期）
│       └─ 否 → ⚠️ 再试1次（选更简单的任务）
│
└─ 部分成功（Review通过但效率未提升）
    └─ 原因是Prompt质量问题？
        ├─ 是 → 改进Prompt后重试
        └─ 否 → ❌ 暂缓，记录障碍重新评估
```

**决策2：是否进入阶段2？**
- ✅ 推进标准：至少1次试点成功 + 团队愿意继续
- ⚠️ 延缓标准：发现重大障碍（工具不支持、代码库问题等）
- ❌ 停止标准：必要条件有变化（例如项目紧急交付压力骤增）

## 🚀 阶段2：扩展期（2-3个Sprint）

### Sprint N：保守扩展（20%任务使用AI）

**任务规划原则**：
1. 用AI编程执行计划提示词（V2.0）对Sprint任务进行分类
2. 选择评分最高的2-3个🟢任务执行
3. 其余任务全部人工执行
4. 预留额外20% Buffer（应对AI任务失败的风险）

**Sprint启动清单**：

```markdown
Sprint N 启动前确认：

□ 使用V2.0提示词完成所有任务的AI执行模式分类
□ 为所有🟢任务编写Prompt（至少提前1天）
□ 已验证Prompt中的文件路径存在且正确
□ 所有🟢任务已在Jira中更新AI相关字段
□ 效果跟踪模板已准备
□ 所有人知道：哪些是🟢任务，谁来执行，什么时候Review
```

**Daily执行流程**（包含AI任务时）：

```
上午开始：
1. 从任务板取一个🟢任务
2. 打开对应的Prompt文件（ai-prompts/sprint-N/US-XXX/T-XXX.md）
3. 粘贴Prompt给AI工具
4. AI执行期间：处理其他人工任务

AI执行完成后：
5. 立即进行Code Review（不要积压！）
   - 对照Review要点逐一检查
   - 运行验证命令（mvn compile, mvn test 等）
6. 填写效果跟踪模板（实时填写，不要事后补）

如果Review不通过：
7a. 问题可修复（<30min）→ 修复后再Review
7b. 问题较多（>30min）→ 记录问题，优化Prompt，下次任务改进
7c. 方向错误 → 降级为🟡，人工接管
```

### Sprint N+1：适度扩展（30-40%任务使用AI）

**新增：开始使用🟡人机协作**

**🟡任务执行标准操作流程**：

```markdown
## 🟡任务执行SOP

### 准备阶段（30min）
1. 准备第1步Prompt（让AI生成初版）
2. 识别关键决策点（提前思考，不要临时决策）
3. 设置迭代计时器（防止无限循环）

### 执行阶段

**轮次1（AI生成初版）**：
- 执行Prompt，获取AI生成的代码和方案说明
- 记录AI选择的方案和理由

**Review（人工，30-60min）**：
判断结果：
- 完全接受 → 记录，进入功能验证
- 需要调整 → 填写反馈表，进入下一轮
- 方向错误 → 记录，转人工主导，不再尝试AI

**反馈表格式**：
```
## AI生成初版反馈

### 接受的部分
- {接受的内容}

### 需要调整的部分
| 位置 | 问题 | 期望 |
|------|------|------|
| {类名/方法名} | {问题描述} | {期望的实现方式} |

### 不接受的部分（需重写）
- {不接受的内容及原因}

### 决策点确认
- {决策点1}：选择 {选项X}，理由：{理由}
```

**轮次2（AI按反馈调整）**：
- 把反馈表提交给AI，让AI按反馈修改
- 如果此轮通过Review → 进入功能验证
- 如果未通过且这是第3轮 → 人工接管

**⚠️ 严格执行：第3轮AI调整未通过 → 立即人工接管，不再尝试第4轮**

**功能验证（人工）**：
- 运行测试套件
- 关键业务场景验证
- 性能测试（如需要）
```

### Sprint N+2：优化迭代（40-50%任务使用AI）

**关键活动：优化Prompt模板库**

基于前两个Sprint的数据：

```markdown
## Prompt模板评级标准

⭐⭐⭐⭐⭐ 精品模板（首次成功率≥80%，已使用≥3次）
⭐⭐⭐⭐ 良好模板（首次成功率60-80%，已使用≥2次）
⭐⭐⭐ 一般模板（首次成功率40-60%，需要调整）
⭐⭐ 待优化（首次成功率<40%）
⭐ 废弃候选（多次使用效果差）

模板库目录结构：
ai-prompts/templates/
├── ⭐⭐⭐⭐⭐-crud-api-springboot.md     # 精品：Spring Boot CRUD API
├── ⭐⭐⭐⭐-unit-test-mockito.md          # 良好：Mockito单元测试
├── ⭐⭐⭐⭐-vue3-component-form.md        # 良好：Vue3表单组件
├── ⭐⭐⭐-dto-validation.md              # 一般：待优化
└── README.md                            # 模板使用指引
```

**调整分类标准**（基于实际数据）：

```markdown
## 评分标准调整记录

### Sprint N+2 调整（基于前2个Sprint数据）

原标准 → 调整后标准：

"前端表单组件"：原评分复杂度3分 → 调整为5分（AI实际效果好）
原因：Vue3+TypeScript的表单组件有高度规律性，AI效果超预期

"数据库Migration"：原评分参考5分 → 调整为3分（参考代码作用有限）
原因：SQL语法AI会，但业务字段的命名需要人工判断

调整后，表单组件任务从🟡升级为🟢。
```

## 🎖️ 阶段3：成熟期（3+个Sprint持续运营）

### 常态化运营机制

**1. 每日例行（5min）**

```markdown
AI任务日常检查：
- 查看当天🟢任务完成状态
- 确认Review未积压（当天完成的任务当天Review）
- 如有阻塞，在日站会提出
```

**2. 每Sprint例行（Sprint回顾会，额外30min）**

```markdown
AI编程效果回顾议题：

1. 数据回顾（10min）
   - 展示效果跟踪模板汇总
   - 实际效率提升 vs 预期效率提升
   - 哪些任务超预期？哪些低于预期？

2. 模板库更新（10min）
   - 新增哪些好用的模板？
   - 哪些模板需要降级或废弃？

3. 分类标准调整（5min）
   - 某类任务是否需要调整分类？

4. 下Sprint目标（5min）
   - 是否增加🟢任务比例？
   - 是否尝试新的任务类型？
```

**3. 每月例行（1小时）**

```markdown
月度AI编程复盘：

1. 累计效率提升趋势图（是否在增长？）
2. Prompt首次成功率趋势（是否在提升？）
3. 模板库规模（是否在积累？）
4. 团队AI能力评估（新成员是否能独立使用？）
5. 与其他团队分享成果（内部推广）
```

### 成熟期健康度指标

**每季度评估以下指标，判断方案是否还在正轨：**

| 指标 | 健康标准 | 告警标准 | 危险标准 |
|------|----------|----------|----------|
| 🟢任务占比 | 40-60% | 20-40% | <20% |
| Prompt首次成功率 | ≥70% | 50-70% | <50% |
| Review返工率（>1轮） | ≤30% | 30-50% | >50% |
| 实际效率提升 | ≥40% | 20-40% | <20% |
| 新成员上手时间 | ≤1周 | 1-2周 | >2周 |

当任意指标进入"危险标准"时，需要专项复盘并制定改进计划。

## ❓ 常见问题FAQ

**Q1: 首个Sprint效率提升为负，是否应该放弃？**

A: 不要放弃。首个Sprint负收益是正常现象，原因是：
- Prompt设计学习成本（首次>后续4倍的时间）
- 工具链配置时间（一次性投入）
- 团队适应期（学习如何Review AI代码）

只要首个Sprint至少有1个🟢任务成功执行（即使总效率为负），就说明方向正确，继续推进。

---

**Q2: AI生成的代码Review失败率很高，怎么办？**

A: Review失败原因通常是以下之一：
1. **Prompt不够具体**（最常见）：增加参考代码路径，明确约束条件
2. **参考代码质量差**：换一个更好的参考文件
3. **任务分类过于乐观**：降级为🟡，补充人工调整
4. **Review标准不一致**：统一Review标准，制作Review Checklist

分析失败类型，针对性改进。连续3个任务失败→触发熔断机制，暂停并分析。

---

**Q3: Prompt设计花的时间比直接写代码还长，正常吗？**

A: 首次设计某类任务的Prompt，时间确实可能超过直接实现。但是：
- 第2次使用同类Prompt：时间降低70%
- 第3次以后：几乎只需要修改变量（任务名、文件路径等）
- 关键是建立模板库，而不是每次都从零开始

建议：对同类任务（如CRUD API），设计1个高质量模板，后续复用。

---

**Q4: 团队成员担心被AI取代，不愿意积极使用，怎么处理？**

A: 这是文化问题，需要从以下角度沟通：
1. **解放时间**：AI处理重复性工作，你的时间用来做更有价值的事（架构设计、业务分析、创新）
2. **提升竞争力**：掌握AI工具是未来必备技能，早学习早受益
3. **数据说话**：展示效率提升数据，让成员看到实际好处
4. **自主可控**：AI生成的代码都经过人工Review，质量责任仍在人身上

关键：不要强制，而是让愿意尝试的成员先试，用成功案例吸引其他成员。
